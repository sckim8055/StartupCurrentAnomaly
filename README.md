# 압력기 시동 전류 이상 감지 실습 (StartupCurrentAnomaly)

공장 유압 프레스(압력기) 전동기가 **시동할 때 들어오는 전류**를 보고, 평소와 다른 시동을 실시간으로 잡아내는 실습이다.
자료 만들기 → 학습 → 평가 → 실시간 적용까지 전 과정을 코드로 따라간다. 모든 코드에 강의용 주석이 달려 있다.

> 이 폴더의 자료는 **시뮬레이션(가짜) 자료**다. 원리를 익힌 뒤 실제 센서 자료로 바꿔 쓰도록 만들었다.

---

## 1. 시나리오

- 전동기는 시동 순간 정격의 약 6배 전류(돌입 전류)가 흐르고, 회전이 붙으면 0.5초 안에 정격 근처로 내려와 안정된다.
- 이 **모양**이 평소와 다르면 설비에 문제가 생기고 있다는 신호다.
- 전류 단위는 정격 대비 배수(p.u.)다. 1.0 = 정격 전류. 센서의 암페어 값을 정격 전류로 나누면 된다.
- 센서는 초당 500번 실효값(RMS) 전류를 읽고, 시동 1건은 시동 후 2초(1000개 값)로 본다.

| 이상 유형 | 파형의 변화 | 현장에서 의심되는 원인 |
|---|---|---|
| 돌입 전류 과다 | 최댓값이 15~50% 큼 | 전원 전압 상승, 접촉기 접점 불량 |
| 기동 지연 | 전류가 1.5~3배 느리게 줄어듦 | 잔압 남은 채 시동(부하 과다), 베어링, 윤활 |
| 순간 전압 강하 | 안정 구간에서 잠깐 푹 꺼짐 | 다른 큰 설비 동시 기동, 배전 문제 |
| 안정 구간 떨림 | 안정 구간이 15~30 Hz로 출렁임 | 축 정렬 불량, 커플링 마모, 펌프 맥동 |
| 결상 | 안정 전류가 1.4~1.8배 | 퓨즈 단선, 단자 풀림 |
| 시동 실패(구속) | 전류가 거의 줄지 않음 | 기계 걸림 |

## 2. 폴더 구조

```
StartupCurrentAnomaly/
├─ config.py         모든 설정값 (샘플링, 시동 감지 기준, 자료 개수, 학습·경보선 설정)
├─ simulate.py       1단계: 시나리오 자료 만들기 → data/
├─ model.py          모델(오토인코더)과 점수·규칙 계산
├─ train.py          2단계: 학습 + 경보선 결정 + 모델 저장 → models/
├─ evaluate.py       3단계: test로 성능 평가 → reports/
├─ detector.py       판정기 (현장에서 쓰는 부분)
├─ run_realtime.py   4단계: 실시간 적용 흉내 (저장된 기록 재생) → logs/
├─ signal_generator.py  5단계: 센서 흉내 — 신호를 끊임없이 네트워크(UDP)로 보냄 (서서히 고장 나는 시나리오)
├─ monitor.py        5단계: 계속 받는 신호에 모델 적용 → 이상 감지 + 앞으로의 이상 예측 → logs/, reports/trend.png
├─ run_all.bat       1~4단계를 한 번에 실행 (윈도우)
├─ run_monitor_demo.bat  5단계 시연: 창 두 개(monitor, generator)를 띄움 (윈도우)
├─ requirements.txt
├─ data/             train.npz · val.npz · test.npz · stream_demo.csv
├─ models/           startup_ae.pt (학습된 모델) · model_summary.json (사람이 읽는 요약)
├─ reports/          test_report.md · test_results.csv · examples.png · training_curve.csv/png
└─ logs/             alarms_날짜.csv (실시간 판정 기록)
```

## 3. 실행

```
pip install -r requirements.txt
python simulate.py        # 자료 만들기 (몇 초)
python train.py           # 학습 (CPU 1분 내외)
python evaluate.py        # test 평가
python run_realtime.py    # 실시간 감지 흉내 (빠르게)
python run_realtime.py --realtime   # 실제 시간 속도로 재생 (약 2분, 강의 시연용)

# 5단계 (창 두 개)
python monitor.py                         # 창1: 신호 받기 + 감지 + 예측
python signal_generator.py --speed 10     # 창2: 신호 보내기 (10배속이면 고장까지 약 1분)
```
윈도우에서는 `run_all.bat` 하나로 1~4단계를 차례로 실행할 수 있다.
data/, models/, reports/ 에는 미리 실행한 결과가 들어 있다. 다시 실행하면 같은 내용으로 덮어쓴다(난수 씨앗 고정).

## 4. 단계별 핵심

### 1단계 — 자료 나누기 (simulate.py)

| 자료 | 내용 | 용도 | 주의 |
|---|---|---|---|
| train | 정상 1200건 | 모델이 정상 모양을 배움 | 정상만 쓴다 |
| validation | 정상 400건 | 학습 멈출 시점, 경보선 결정 | 학습에 쓰지 않는다 |
| test | 정상 400건 + 이상 6종 × 40건 | 마지막 성능 평가 1회 | 결정에 절대 쓰지 않는다 |

학습에는 **정상 자료만** 쓴다. 현장에는 정상 자료가 대부분이고 고장 자료는 드물기 때문이다.
이상 자료는 "정말 잡는지" 확인하는 test에만 쓴다.

### 2단계 — 학습 (train.py, model.py)

- **오토인코더**: 파형 1000개 값을 숫자 16개로 압축했다가 다시 그린다. 정상만 배웠으므로 이상 파형은 잘 못 그린다 → **복원 오차가 크면 이상**.
- **조기 종료**: validation 오차가 20바퀴 동안 좋아지지 않으면 멈추고, 가장 좋았던 순간의 가중치를 쓴다.
- **경보선**: validation(정상)의 구간별 오차 중 상위 0.5% 위치 × 1.2.
- **간단한 기준(규칙)**: 최대 전류·안정 전류·감쇠 시간이 train 평균 ± 5 표준편차를 벗어나면 이상.
  감쇠 시간 = 최댓값에서 전류가 37%(1/e) 수준까지 내려가는 데 걸린 시간. 정상은 약 0.12초.
- 모델·정규화 값·경보선·규칙 범위를 **한 파일**(`models/startup_ae.pt`)에 함께 저장한다. 버전이 섞이는 사고를 막기 위해서다.

### 3단계 — 평가 (evaluate.py)

미리 실행한 결과 (`reports/test_report.md`):

| 실제 상태 | 모델만 | 규칙만 | 둘 중 하나(최종) |
|---|---|---|---|
| 정상 (오경보율) | 3/400 (1%) | 0/400 (0%) | 3/400 (1%) |
| 돌입 전류 과다 | 23/40 (58%) | 33/40 (82%) | 33/40 (82%) |
| 기동 지연 | 40/40 | 40/40 | 40/40 |
| 순간 전압 강하 | 37/40 (92%) | 0/40 | 37/40 (92%) |
| 안정 구간 떨림 | 34/40 (85%) | 0/40 | 34/40 (85%) |
| 결상 | 40/40 | 40/40 | 40/40 |
| 시동 실패 | 40/40 | 40/40 | 40/40 |

전체: 정밀도 0.987, 재현율 0.933, F1 0.959.

**읽는 법 (강의 포인트)**
- 모델은 **모양 변화**(기동 지연, 전압 강하, 떨림)를 잘 잡고, 규칙은 **크기·시간 변화**(돌입 과다, 결상, 기동 지연)를 잘 잡는다. 그래서 둘을 함께 쓴다.
- 돌입 전류 과다는 둘 다 써도 82%다. 놓친 7건은 모두 최대 전류가 6.35 이하로, 규칙의 정상 범위(4.2~6.39) 안에 들어온 경우다. 원래 돌입 전류가 낮던 시동이 조금 커진 것이라 평소 흔들림과 구별이 안 된다.
- `reports/examples.png`를 보면 모델이 돌입 과다 파형을 **너무 잘 다시 그린다**. 오토인코더는 크기만 바뀐 파형은 그대로 따라 그릴 수 있어서, 복원 오차만으로는 놓친다. 이것이 규칙이 필요한 이유다.
- 판정은 현장과 같은 함수(`detector.judge`)로 한다. 평가와 현장 동작이 어긋나지 않게 하기 위해서다.

### 4단계 — 실시간 적용 (detector.py, run_realtime.py)

```python
det = StartupDetector()            # 프로그램 시작 때 한 번: 모델 파일 불러오기
for x in 센서_값들:                  # 값이 하나 들어올 때마다
    result = det.feed(x)           # 시동 2초가 모이기 전에는 None
    if result and result["alarm"]:
        경보_조치(result)            # 어느 구간이 이상한지 result["where"]에 있음
```

판정기 내부 순서:
1. 대기 중에 전류가 0.5(TRIGGER)를 넘으면 시동 시작 → 기록 시작
2. 2초(1000개)가 모이면 모델 + 규칙으로 판정 (1건에 수 ms)
3. 전류가 0.2(REARM) 아래로 내려가 전동기가 멈춘 뒤에야 다음 시동을 기다린다
   - 이 단계가 없으면 판정 후에도 돌고 있는 전동기 전류(≈1.0)를 새 시동으로 착각한다. 실제로 처음 만들 때 이 실수로 오경보가 쏟아졌다. 강의에서 꼭 짚을 부분이다.

미리 실행한 결과: 시동 52건 중 정상 40건 오경보 0, 이상 12건 모두 경보.

### 5단계 — 계속 들어오는 신호로 감지 + 예측 (signal_generator.py, monitor.py)

**신호 보내기 (`signal_generator.py`)** — 센서처럼 신호를 끊임없이 보낸다. 받는 쪽이 없어도 계속 보낸다.
- 처음 60회 시동은 새 설비. 그 뒤 140회에 걸쳐 베어링이 서서히 닳아(감쇠가 느려지고 떨림이 생김) 200회째 무렵 시동 실패(고장).
- 시동마다 3% 확률로 순간 전압 강하(다른 설비 탓 — 미리 알 수 없는 일)가 섞인다.
- 정답(열화 정도)은 보내는 창에만 보인다. 받는 쪽은 전류 값만 받는다.
- UDP로 0.1초 분량(50개)씩 보낸다. 묶음 번호로 빠진 신호를 알아채고, 빠진 시동은 판정하지 않는다.

**받아서 감지·예측 (`monitor.py`)**
1. **감지**: 4단계와 같은 판정기로 시동마다 즉시 판정한다.
2. **예측**: 시동마다 '건강 지표' 두 가지를 기록하고, 최근 80회에 2차 곡선을 맞춰 경보선(= 1)에 닿을 시점을 계산한다.
   - (가) 모델 지표 = 오토인코더 점수 ÷ 경보선
   - (나) 감쇠 지표 = 감쇠 시간 ÷ 정상 범위 위 끝
   - 도달이 30회 이내로 예상되면 `◆ 예측 주의`를 띄운다.
3. 끝나면 "예측이 실제와 맞았나"를 스스로 확인해 출력하고, `reports/trend.png`를 그린다.

**결과 (시나리오 8번 반복, 씨앗 1~8)** — 감쇠 지표가 3회 연속 경보선을 넘은 시점을 몇 회 전에 얼마나 맞혔나 (+ = 늦게 예측, - = 일찍 예측, - 표시 없음 = 예측 못 냄)

| 몇 회 전에 낸 예측 | 40회 전 | 30회 전 | 20회 전 | 10회 전 | 5회 전 |
|---|---|---|---|---|---|
| 감쇠 지표, 8번 중 예측을 낸 횟수 | 1 | 6 | 8 | 8 | 8 |
| 감쇠 지표, 오차 범위 | +13 | -14 ~ +40 | -12 ~ +12 | -6 ~ +4 | -5 ~ +4 |
| 모델 지표, 8번 중 예측을 낸 횟수 | 0 | 0 | 0 | 0 | 1 |

**읽는 법 (강의 포인트)**
- **감지는 모델이 빠르다.** 모델 경보는 시동 120~132회 무렵부터 이어진다. 고장(200회)보다 약 70회 앞이다.
- **예측은 감쇠 지표만 된다.** 모델 점수는 정상 범위에서 들쭉날쭉하다가 경보선 근처에서 갑자기 뛰어서, 추세로 미리 알려 주지 못한다.
  감쇠 시간은 고장 원리(회전이 무거워짐 → 감쇠가 느려짐)와 바로 이어져 있어서 꾸준히 올라간다.
  → **잡는 데 좋은 지표와 미리 아는 데 좋은 지표는 다를 수 있다.**
- 10~20회 전 예측은 대체로 ±12회 안에 들지만, 30회 이상 앞은 크게 빗나가기도 한다. 멀리 볼수록 불확실하다.
- **갑자기 생기는 일(순간 전압 강하)은 예측할 수 없다.** 직전까지 흔적이 없으므로 감지만 된다.
- **2차 곡선이 잘 맞는 이유는 이 시나리오의 열화를 2차식으로 만들었기 때문이다.** 실제 설비에서는 어떤 곡선이 맞는지 실제 자료로 다시 확인해야 한다. 직선으로 이어 그리면 도달 시점을 늦게 예측하는 경향이 있었다(늦은 예측은 위험하다).
- 시나리오 신호에서는 새 설비 구간(60회)에도 모델 경보가 몇 번 났다(점수비 1.0~1.3 근처, 약 5%). test 자료의 1%보다 높다. 실제 운영에서는 "3회 연속" 같은 조건을 붙여 한 번 튄 경보와 구별한다.

## 5. 실제 현장에 적용하는 방법

**현장 PC에 가져갈 파일**: `config.py`, `model.py`, `detector.py`, `models/startup_ae.pt` (+ 실시간 실행 파일)

**바꿀 곳은 두 군데**
1. 신호 입력 — `run_realtime.py`의 `sensor_stream()`(Modbus TCP 예시가 주석에 있음), 또는 센서 쪽에서 `signal_generator.py`와 같은 형식(UDP, JSON)으로 보내게 하고 `monitor.py`를 그대로 쓴다.
2. 조치 — `act()` 또는 `monitor.py`의 출력 부분을 경보등, 메신저 알림, 정비 요청, PLC 신호 등으로 바꾼다.

**실제 자료로 바꾸는 순서**
1. 시동 신호에 맞춰 전류 파형을 모은다. 같은 센서, 같은 샘플링 속도, 같은 단위(p.u.)여야 한다.
2. 정비 기록을 보고 **정상인 시동만** 골라 train·validation으로 나눈다. **날짜 순서로** 나눈다(앞 기간 train, 뒤 기간 validation).
3. 과거 고장·이상 기록이 있으면 test에 넣어 실제로 잡는지 확인한다. 없으면 한동안 경보만 기록하고, 현장 확인 결과로 판단한다.
4. `simulate.py` 대신 그 자료를 `data/train.npz` 등 같은 형식으로 저장하고 `train.py`부터 그대로 실행한다.

**운영**
- 경보선은 오경보 비용과 놓침 비용을 보고 조정한다 (`THRESHOLD_QUANTILE`, `THRESHOLD_MARGIN`). 오경보가 너무 잦으면 결국 아무도 경보를 보지 않는다.
- 설비 교체·정비 후, 또는 계절이 바뀌어 정상 모양이 달라지면 정상 자료로 다시 학습한다. 학습은 밤에 사무실 PC에서 하고, 현장에는 새 모델 파일만 바꿔 넣는다.
- 예측(`monitor.py`)은 '서서히 나빠지는 고장'에만 쓸 수 있다. 어떤 지표가 그 고장과 이어져 있는지는 설비 원리와 과거 고장 기록으로 정한다.

## 6. 주의와 한계

- **가짜 자료의 결과다.** 실제 파형은 온도·부하·전원 상태가 훨씬 다양하다. 위 숫자를 실제 성능으로 기대하면 안 된다.
- **AI는 조기 경보다.** 과전류 계전기 같은 기존 보호 장치를 대신하면 안 된다. 안전 정지는 하드웨어 보호가 맡는다.
- **이상 위치 표시는 대략적이다.** 전압 강하처럼 짧은 이상도 여러 구간에 걸쳐 표시될 때가 있다.
- **처음 보는 유형**은 잡을 수도, 못 잡을 수도 있다. 정상과 다르면 잡을 가능성이 높지만, 크기만 다른 변화는 규칙이 필요하다.

## 7. 실습 과제 예시

1. `THRESHOLD_QUANTILE`을 0.99 / 0.999로 바꾸면 오경보율과 감지율이 어떻게 바뀌는가?
2. `LATENT`를 4 / 64로 바꾸면? (너무 크면 이상도 잘 다시 그려서 오히려 못 잡을 수 있다)
3. `simulate.py`에 새 이상 유형(예: 시동 중 전류가 두 번 치솟음)을 추가하고, 학습을 다시 하지 않고도 잡히는지 확인하라.
4. `config.py`의 `REARM`을 0으로 바꿔 실시간 감지를 돌려 보고, 무슨 일이 생기는지 설명하라.
5. train에 이상 자료를 5% 섞어 학습하면 성능이 어떻게 바뀌는가? (현장 자료에는 모르는 이상이 섞여 있기 마련이다)
6. `monitor.py`의 `forecast()`를 2차 곡선 대신 직선(`np.polyfit(..., 1)`)으로 바꾸면 예측 오차가 어떻게 바뀌는가? 왜 그런가?
7. `signal_generator.py`의 `SUDDEN_PROB`를 0.3으로 올리면 감지와 예측이 각각 어떻게 흔들리는가?
